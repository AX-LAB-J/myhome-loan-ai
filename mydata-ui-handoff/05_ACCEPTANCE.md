# 05. 검수와 완료 기준

각 검수는 `통과 / 실패 / 미실행 / 차단 / 해당 없음` 중 하나와 근거를 기록한다. ‘해당 없음’에는 이유가 필요하다. 실개인정보를 테스트 fixture나 공개 스크린샷으로 복사하지 않는다.

## 1. 시각·모바일 검수

| ID | 검수 | 통과 기준 |
|---|---|---|
| V01 | Figma 대조 | S01~S10을 기준 폭에서 비교. 카드 순서·텍스트·색·활성 상태·버튼 위치가 대응 |

## 2. 버튼 완전성

`01_UI_SPEC.md`의 C/H/N/L/G/M/P/F/A/D/Q ID를 모두 `traceability.md`에 옮긴다.

- 링크는 실제 목적 화면을 연다. `href="#"`, 빈 함수, 로그만 출력하는 버튼은 완료가 아니다.
- 메뉴·뒤로가기·목록↔지도·시트 닫기는 기존 상태를 적절히 복원한다.
- 입력 필드의 단위/유효값/비활성 상태가 일치한다.
- 필터·정렬은 실제 결과와 건수를 바꾼다.
- 저장·새로 불러오기·되돌리기는 실제 상태와 계산을 갱신한다.
- 주석에 따라 삭제한 컨트롤은 ‘삭제 — 결정 ID/근거’로 남긴다. 구현에서 빠뜨린 것과 구분한다.
- 원본에 펼친 화면이 없는 요소도 필요한 최소 동작을 정의해 검수한다.

## 4. 계산 검수

기대 금액은 기존 계산 규칙을 확인한 뒤 독립적인 기준 사례로 작성한다. 구현 함수의 결과를 그대로 기대값으로 복사하는 테스트는 피한다.

| ID | 사례 | 검수 포인트 |
|---|---|---|
| K01 | 정상 재무정보/기본 가정 | 홈 경계·최대·잔여금의 기준 결과 일치 |
| K02 | 각 구간 경계 직전/정확히/직후 | 포함 관계와 표시 반올림 일관성 |
| K03 | 소득/자산/대출/지출 누락 | 계산 불가 또는 정의된 부분 결과, 0 대체 금지 |
| K04 | 대출 0·자산 0·금리 0 등 허용 경계 | NaN/Infinity/오류 없이 명시 규칙 처리 |
| K05 | 기존 대출 상환 포함 지출 | 이중 차감 없음 |
| K06 | 예비비/기타 동원 자금 변경 | 가용 자금과 구매력에 정의된 영향 반영 |
| K07 | 한도대출 포함 on/off | 금리 활성 및 계산 입력이 함께 변함 |
| K08 | 금리 +1%p 상세 비교 | 원금·만기 고정, 금리만 변경 |
| K09 | 예상 대출 범위 | 금리별 가능 대출 산출이며 K08과 구별 |
| K10 | 목표 여유자금/상환 상한 변경 | 실제 경계·분류·검색 조건 갱신 |
| K11 | 같은 조건, 4화면 비교 | 홈 문맥·목록·지도·상세 버전과 해당 값 일치 |
| K12 | 자금 부족/음수 잔여금 | 경고·구간·부족액이 모순되지 않음 |

주거비 제외를 유지할지에 대한 D07 결정 전에는 관련 계산을 임의로 제거하지 않는다.

## 5. 통합 시나리오

### E01 — 기본 탐색

테스트 사용자 진입 → 홈 DB/계산값 확인 → 메뉴 열기/닫기 → ‘이 범위에서 지역 찾기’ → 지역·면적·기간 변경 → 목록 필터/정렬 → 단지 선택 → 상세 → 뒤로가기.

기대: 실제 버튼이 동작하고 동일 문맥의 값이 일치하며 목록 필터·스크롤이 복원된다.

### E02 — 재무정보 저장

S07 기타 동원 자금 변경 → 저장 → 새 계산 버전 → 홈·단지 결과 갱신 → AI 새 세션 확인 → 새로고침.

기대: 저장값 유지, 출처 구분, 재계산 반영, 오래된 AI 대화가 새 기준처럼 노출되지 않음. 실패를 주입하면 입력 유지·오류 안내·성공 초기화 없음.

### E03 — 가정 변경과 초기화

목표 여유자금·예비비·금리/만기 변경 → 한도대출 off/on → 금리 비교 옵션 → 저장 → 상세 비교 → 기본값으로 → 확정한 정책에 따라 저장.

기대: 필드 활성 상태·기본값/수정됨 표시·계산·채팅 새 시작 모두 일치. 기본값은 실제 설정 출처와 같음.

### E04 — 지도·목록 연속성

목록 조건 선택 → 지도 → 구 범위 칩 변경 → 구 선택 → 확대 → 단지 마커 선택 → 상세 → 뒤로 → 목록.

기대: 필터 유지, 거래수 정의 일치, 구/마커 선택 올바름, 지도 줌/위치 복원. 지도 실패 시 목록 접근 가능.

### E05 — LLM 성공/미지원

‘월 상환 150만원 이하인 집만 보여줘’ → 구조화 조건/실제 필터 확인 → 조건 칩/변경 전후 설명 → 바뀐 결과 보기 → 다시 채팅 → 되돌리기.

‘강남 출퇴근 50분 이내로 찾아줘’는 시간 데이터가 없으면 미지원 안내하고 기존 조건 유지. ‘목표 여유자금 바꾸기’처럼 수치가 없으면 질문한다.

기대: LLM 말풍선뿐 아니라 실제 상태가 변함. 테스트의 150만원은 기획 예시이며 제품 기본값으로 저장하지 않음.

### E06 — 채팅 상태 경계

조건 2개 적용 → 1개 칩 삭제 → 과거 응답 되돌리기 시도 → 시트 닫기/재열기 → 새로 시작 → 폼 저장.

기대: 삭제 대상만 제거, 과거 버전 충돌 처리, 닫기는 유지, 새 시작은 D08 정책, 폼 저장은 원본대로 새 대화.

### E07 — 연결 관리

연결 상태/기관/동의 열기 → 다시 불러오기 → 성공/실패 확인 → 테스트 계정에서 연결 해제 확인 취소 → 실제 테스트 해제.

기대: 동기화 출처/날짜 갱신, 직접 입력 보존 정책 준수, 취소 시 변화 없음, 해제 후 가져온 정보 처리와 계산 중지. 공용 원천 데이터는 손상되지 않음.

### E08 — 사용자 격리와 늦은 응답

테스트 사용자 A의 느린 계산/채팅/조회 실행 → 허용된 선택 기능으로 B 전환 → A 응답 도착.

기대: B 화면에 A 데이터가 보이지 않음. 직접 API로 다른 사용자 ID를 넣어도 권한 검증. 실고객 대상으로 시험하지 않음.

### E09 — 집계 표본 억제

최소 표본수 미만/정확히/초과 fixture로 시장 참고 및 비슷한 조건 구매자 확인.

기대: 서버가 미만 집계값을 반환하지 않거나 명시 억제. 개별 사례가 UI·LLM에 노출되지 않음. 임계 수치가 미정이면 완료 불가로 기록.

### E10 — 동시 요청과 장애

빠른 필터 연속 변경, 저장 버튼 반복 클릭, LLM 재시도, 재계산 실패, 서버 재시작/새로고침.

기대: 늦은 결과가 최신 상태를 덮지 않음, 조건/저장 중복 적용 없음, 실패 원인 표시, 마지막 유효 상태와 기준 버전 유지.

## 6. 테스트 실행 전략

- 프로젝트의 기존 테스트 도구를 먼저 사용한다.
- 계산·단위·사용자 범위·상태 변경은 자동 테스트 우선. 단순 색상 변경마다 구현을 그대로 따라 쓰는 테스트를 만들지는 않는다.
- LLM은 도구 계층을 결정적으로 테스트하고, 제한된 실제 API 호출로 연동을 확인한다. 고정 문장 일치보다 구조화 조건·상태·수치 일치를 검증한다.
- 지도는 SDK 로딩/실제 상호작용을 확인하고 데이터 집계는 별도 테스트한다.
- 외부 API를 못 호출한 경우 fixture 테스트 통과와 실연동 미검증을 구분한다.
- 검수 중 실제 사용자 데이터 삭제·운영 초기화·의도하지 않은 대규모 외부 호출을 하지 않는다.
