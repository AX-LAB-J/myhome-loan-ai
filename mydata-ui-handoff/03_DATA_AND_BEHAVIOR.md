# 03. 데이터 계약과 동작 설계

이 문서의 이름과 구조는 **구현 제안**이다. 기존 API/스키마를 조사한 뒤 동일한 의미를 담는 방식으로 적용한다. 실제 DB 테이블을 새로 만들라는 지시가 아니다.

## 1. 시스템 책임

```text
React 모바일 UI
  └─ 기존 인증/사용자 문맥 + FastAPI
       ├─ DB 조회·집계·사용자 입력 저장
       ├─ 단일 계산 서비스 → 구매력/현금흐름/금리 시나리오
       ├─ 부동산 검색·지도 집계
       ├─ LLM 조건 해석 → 검증된 변경 → 계산기 → 결과 설명
       └─ 마이데이터 연결·동기화·동의 처리

네이버 지도 JS 표시 ← 좌표·경계·단지 상태(앱 API)
OpenAI 서버 호출 ← 필요한 최소 문맥, 허용된 조건 스키마
```

- 프론트는 서버 계산 결과를 포맷하고 표시한다. 각 화면에서 별도 구매력 공식을 구현하지 않는다.
- 기존 계산기와 데이터 모델을 우선 재사용한다. 기획과 불일치하는 로직은 근거를 찾고 테스트를 먼저 정의한 후 수정한다.
- LLM은 원천 DB에 직접 쓰거나 임의 SQL을 실행하지 않는다. 허용된 도구/필드만 사용한다.
- 실제 개인정보 표시 요청은 다른 고객 정보나 전체 금융 원장을 LLM에 보내라는 허가가 아니다. UI 표시와 LLM 입력을 별도 계약으로 설계한다.

## 2. 화면용 데이터 묶음

| 제안 개념 | 포함할 의미 | 쓰는 화면 |
|---|---|---|
| UserContext | 인증된 사용자/가구, 표시용 고객 ID, 합성 여부 | 전체, S02 |
| FinancialSnapshot | 나이/주택/소득/지출/자산/계좌/기존 대출/직접 입력, 각 출처·기준일 | S07, 계산 입력 |
| Assumptions | 목표 여유자금·예비비·금리·만기·한도대출 설정·비율·비용률·비교 설정 | S01/S08 |
| AffordabilitySnapshot | 구간 경계·최대·기준 월 현금흐름·사용 가정·계산 버전 | S01/S03~S06 |
| SearchContext | 지역·면적·기간·구간·정렬·목록/지도·지도 범위·선택 단지 | S03~S06 |
| PropertySummary/Detail | 단지·면적·참조 가격·거래수·기준일·개인화 구간·자금계획 | S03/S05/S06 |
| DistrictAggregate | 구 경계/코드·거래수·예산 안 수·비율·구간분포·표본 상태 | S04 |
| CohortAggregate | 비교 조건·표본수·공개 여부·비중 중앙값·기준일 | S03/S06 |
| ConnectionState | 연결 상태/기관/동의/최근 동기화 | S02/S07/S09 |
| ConversationState | 세션·메시지·적용 조건·적용 전후 버전·되돌리기 가능 여부 | S10 |

**가능하면 모든 개인화 결과에 같은 기준 문맥을 포함:** 사용자/가구, 재무정보 버전, 가정 버전, 조건 버전, 계산 결과 버전, 부동산 데이터 기준일. 정확한 필드명이나 저장 방식은 기존 구조에 맞춘다.

서버가 같은 요청 문맥으로 계산한 결과만 함께 표시한다. 저장 직후 홈은 새 값인데 지도는 옛 값인 상태를 성공 상태로 보여주지 않는다.

## 3. 금액·단위·빈값 계약

- DB가 원/만원/억원 중 어느 단위를 쓰는지 필드별로 확인한다. 화면에는 원본대로 억원 또는 만원을 표시한다.
- [제안] API에서 원 단위 정수 또는 Decimal을 일관되게 사용하되, 기존 계약을 바꾸는 비용이 크면 명시적인 어댑터로 변환한다. 큰 숫자는 JavaScript 안전 정수 범위를 검토하고 필요하면 문자열 기반 Decimal 계약을 사용한다.
- 화면용 반올림 값으로 구간을 판정하지 않는다. 원시 계산값으로 구간을 결정하고 표시만 반올림한다.
- 금리의 `%`와 비율 소수값(예: 0.04)의 차이를 계약에 명시한다. `+1%p`는 금리 수치에 1퍼센트포인트를 더하는 것이며 1%를 곱하는 것이 아니다.
- 기간은 년/개월, 면적은 ㎡, 거래수는 건, 단지수는 곳, 월 금액과 일시금은 별도 의미다.
- `null/미제공`, `0`, `음수`, `계산 불가`를 구분한다. 정보가 없는데 ‘0만원’, ‘안정권’으로 표시하지 않는다.
- API 실패와 정상 빈 결과를 다른 상태로 처리한다. 오류 메시지에 연결 문자열·키·개인정보를 포함하지 않는다.
- 기준일은 데이터 기준일과 동기화 시각을 구분한다. 화면마다 현재 날짜로 하드코딩하지 않는다.

## 4. 계산기 계약과 불변 조건

### 원본이 설명하는 개념

- 안정권은 목표 여유자금과 연관된다. 가능권은 목표보다 적게 남는 구간, 한계권은 현재 지출 유지 시 적자, 범위 밖은 계산상 최대 초과로 표현된다.
- 필요 자기자금은 집값+부대비용−예상 대출, 가용 자금은 예비비를 뺀 금액으로 설명된다.
- 금리 비교 표는 대출 원금과 만기를 고정하고 금리만 바꾼다.
- 예상 대출 범위는 현재 금리와 +1%p의 조건별 대출 가능량을 비교한다.
- 화면의 상한 비율은 ‘계산 가정’이며 실제 규제/승인 결과라는 뜻이 아니다.

### 현지에서 확인해야 할 규칙

1. 구매력 경계 계산과 상한 우선순위, 각 경계의 포함/미포함.
2. 자산 부족·현금흐름 부족·대출 조건 초과가 함께 발생할 때 구간 분류.
3. 큰 홈 금액의 정확한 의미와 ‘계산상 최대’의 관계.
4. 월소득의 정의, 총지출에 기존 대출 상환/주거비 포함 여부.
5. 금융자산 중 현금화 가능 금액, 기타 동원 자금, 예비비·부대비용 처리.
6. 한도대출 잔액/약정한도/추가 조달 가능액과 상환 부담 반영.
7. 부대비용의 계산 기준과 대출 범위 양 끝을 구하는 방식.
8. 채팅 월 상환 상한이 총 상환액인지 신규 주담대인지.
9. 금리 스트레스 사용 여부가 홈·지도·상세에 미치는 영향.

확정 공식이 없으면 기획 설명만으로 임의 금융 공식을 완성하지 않는다. UI 구조·상태·데이터 연결은 진행하고, 금액 정확성 완료는 계산 규칙이 확정될 때까지 보류한다.

### 검증할 불변 조건

- 같은 사용자·단지·면적·기간·조건 버전이면 목록/지도/상세의 가격·구간·잔여금이 같다.
- 사용 금액을 분해한 합계가 화면 총액과 일치하며 각 항목이 한 번만 차감된다.
- 기존 대출 상환이 지출에도 포함됐다면 별도로 또 차감하지 않는다.
- 예비비 증가가 다른 조건 동일 상태에서 가용 자금을 늘리지 않는다.
- 금리 +1%p 비교는 다른 조건 동일 상태에서 동일 양수 원금의 원리금균등 상환액을 낮추지 않는다. 0원금 등 경계 사례는 별도 처리한다.
- 한도대출 금리가 비활성 상태면 숨은 이전 입력값이 계산에 영향을 주지 않는다.
- 단순 구간 막대 비율로 대출이나 가격을 역산하지 않는다.

## 5. 필요한 서비스 동작 목록

경로/HTTP 메서드는 실제 API와 맞춘다. 기존 핸들러가 부족할 때 아래 의미만 충족하도록 확장한다.

| 작업 | 입력 의미 | 결과 의미 |
|---|---|---|
| 현재 사용자 조회 | 인증 문맥 | 표시 사용자·가구·권한·데이터 모드 |
| 재무정보 조회 | 사용자/가구 범위 | 출처/기준일 포함 스냅샷 |
| 재무정보 수정 | 허용 직접입력·수정 필드, 기준 버전 | 저장 상태·계산 상태·새 버전 |
| 가정 조회/저장/기본값 | 사용자 가정과 버전 | 기본값/수정 여부·새 계산 결과 |
| 구매력 조회/시나리오 | 재무정보·가정·조건 버전 | 일관된 구간·현금흐름 |
| 단지 검색 | 지역·면적·기간·구간·정렬·페이지 | 단지수·개인화 카드 |
| 단지 상세 | 단지/면적/기간·계산 문맥 | 자금계획·금리 비교·출처 |
| 지도 집계/마커 | 범위/줌·공통 검색 조건 | 구별 집계 또는 단지 마커 |
| 비교집계 조회 | 허용된 집계 조건 | 억제 여부·표본수·공개 통계 |
| 연결 상태/동의 조회 | 현재 사용자 | 기관·상태·동의 문서·일시 |
| 동기화 | 현재 사용자·중복 방지 키 | 동기화 상태·기준일·갱신 버전 |
| 연결 해제 | 현재 사용자·확정된 해제 범위 | 해제/삭제 완료 상태·계산 무효화 |
| 채팅/조건 변경 | 메시지·세션·기준 버전 | 해석 상태·적용 결과·설명·버전 |
| 조건 삭제/되돌리기/새 시작 | 대상 조건/변경 ID·버전 | 일관된 새 상태 |

모든 개인 API에서 서버가 인증/허용된 개발 사용자 문맥을 확인한다. 프론트에서 전달한 임의 고객 ID를 신뢰해 조회하지 않는다.

## 6. 상태 변경과 일관성

### 재무정보/가정 저장

```text
폼 초안 → 검증 → 저장 및 계산 요청 → 성공 결과 확정
  → 새 계산 버전으로 홈/목록/지도/상세 갱신
  → 새 재무·가정 기준의 AI 세션 시작
  → 사용자에게 완료 표시
```

- 작은 동기 계산이면 하나의 성공 계약으로 묶는 방식이 적합하다. 시간이 걸리는 기존 구조라면 작업 ID와 진행/실패 상태를 사용한다.
- 저장은 됐지만 계산이 실패할 수 있는 구조에서는 그 상태를 명시하고 재계산 재시도를 제공한다. 전체 성공처럼 표시하지 않는다.
- 저장 실패 전에 채팅을 먼저 지우지 않는다. 새 세션 시작은 성공한 기준 버전과 연결한다.
- 현재 입력값이 변경된 폼에서 이동/채팅 진입 시 [제안] 저장 전임을 알리고 초안을 유지한다. 자세한 정책은 D14에 기록.
- 반복 저장·재시도는 중복 기록/채팅 초기화를 유발하지 않도록 멱등 처리를 검토한다.

### 데이터 다시 불러오기

- F02와 D02는 같은 작업을 사용한다. 성공한 시각과 실제 데이터 기준일을 구분한다.
- 원천값 갱신과 직접 입력값 유지/충돌 정책을 문서화한다. 원천값을 수정 입력으로 덮어쓰지 않는다.
- 재수집된 값이 계산 입력에 영향을 주면 기존 개인화 결과를 무효화한다. 채팅 초기화 정책은 D12에서 확정한다.

### 사용자 바꾸기

- 합성 데모 선택기인지 실제 인증인지 먼저 판별한다.
- 교체 시 진행 요청 취소·캐시 키 교체·폼/계산/채팅 초기화 후 새 사용자 값만 표시한다.
- 이전 사용자의 늦은 응답이 새 화면에 반영되지 않게 사용자/버전 확인을 적용한다.

### 연결 해제

- 개발 환경에서는 테스트 계정으로만 검증한다.
- 확정된 범위의 가져온 데이터/연결을 처리한 뒤 계산·개인화 캐시·관련 채팅 문맥을 무효화한다.
- 외부 해제와 앱 데이터 정리가 부분 실패할 수 있으면 상태를 분리하고 재시도 가능하게 한다.
- 삭제 범위·보존 의무·원천 DB 영향은 기존 정책을 확인한다. 기획의 ‘지워짐’을 근거로 고객/기관/공용 거래 DB 전체를 삭제하지 않는다.

## 7. LLM 설계

### 역할

LLM은 자연어를 제한된 조건 변경으로 변환하고, 도구가 반환한 결과를 설명한다. 기존 OpenAI 연동을 재사용하고 모델/SDK를 임의로 변경하지 않는다. 사용 중인 인터페이스에 맞춰 구조화 결과 또는 도구 호출을 적용한다.

### 처리 순서

1. 인증된 사용자·현재 화면·선택 단지·현재 조건·기준 버전 확인.
2. 지원 기능 목록을 기준으로 의도를 분류: 조회/설명, 조건 변경, 추가 질문 필요, 미지원.
3. 숫자·단위·대상·유효 범위를 서버에서 검증. LLM 출력은 신뢰된 값이 아니다.
4. 허용 변경만 적용하고 계산/검색 서비스를 실행.
5. 성공한 전후 결과를 근거로 적용 안내·조건 칩·되돌리기 토큰/변경 ID 제공.
6. 실패/미지원이면 적용했다고 말하지 않고 이전 유효 상태 유지.

### 지원 후보 — 실제 기존 기능을 확인 후 확정

| 의도 | 허용 후보 | 미확정 점 |
|---|---|---|
| 월 상환 상한 | 명시 금액 상한 | 신규/전체 상환 기준 |
| 목표 여유자금 | 월 금액 수정 | 지속 저장인지 세션 조건인지 |
| 예비비 | 남겨둘 현금 수정 | 금액이 없으면 질문 |
| 금리 상승에도 가능한 곳 | 스트레스 시나리오 필터 | ‘괜찮은’ 구간의 기준 |
| 지역·면적·거래기간 | 기존 검색 옵션 | 실제 데이터가 지원하는 값만 |
| 결과 설명 | 계산 스냅샷 읽기 | 숫자 재생성 없이 사용 |
| 출퇴근 시간 | 원본에서는 미지원 예시 | 시간 데이터/계산 서비스가 없으면 미지원 유지 |

조건 스키마 예시 개념: `status`, `changes`, `unsupportedReason`, `baseVersion`, `resultVersion`, `changeId`, `canUndo`. 실제 필드 이름은 기존 계약에 맞춘다.

### 되돌리기/새 시작

- 변경별 이전 값과 적용 버전을 저장하여 Q04가 실제 상태를 되돌릴 수 있게 한다.
- 과거 응답의 되돌리기가 더 최근 수정을 덮어쓰지 않게 제한하거나 충돌을 안내한다.
- 칩 삭제는 해당 조건만 제거한다. 다른 기본 가정/조건은 유지한다.
- X 닫기는 초기화가 아니다. Q02 ‘새로 시작’의 조건 초기화 범위는 D08로 결정한다.
- F04/A09 저장 성공 후 새 AI 대화를 시작한다는 원본 요구는 반드시 구현한다.

### 개인정보와 신뢰 경계

- LLM에 필요한 것은 보통 계산에 사용한 요약 값과 조건이다. 성명·주민번호·계좌번호·원장 전체를 기본 문맥에 넣지 않는다.
- 구매자 비교에는 비식별 집계만 사용한다. 작은 집단 억제는 서버에서 적용한다.
- 사용자 메시지/DB 텍스트에 포함된 지시로 권한·도구 범위를 변경하지 않는다.
- 설정 수정 도구와 원천 금융정보 변경 도구를 혼동하지 않는다. 모델이 임의 거래/원천 잔액을 수정할 수 없게 한다.

## 8. 지도·목록의 공통 계약

- 동일한 검색 문맥을 공유한다. 지도↔목록 이동으로 지역/면적/기간/개인화 구간이 초기화되지 않는다.
- 히트맵은 거래 수, 목록은 단지 수다. 같은 숫자로 억지 정합시키지 않고 각 정의를 보여준다.
- 거래 기간·면적 필터를 집계에도 적용한다. 분모와 분자에는 같은 데이터 집합 기준을 사용한다.
- ‘표본 부족’과 ‘거래 0건’은 별개다. 최소 표본수·누락 여부를 응답에 구분한다.
- 지도 줌 임계값, 경계 스타일, 마커 선택, 카드, 키보드/터치 동작을 현지에서 검증한다.
- SDK는 지도 표시, 앱 API는 개인화 수치와 도메인 데이터의 역할을 맡는다.
- 좌표가 없는 단지를 임의 위치에 놓지 않는다. 목록에는 표시할 수 있으면 지도 누락 사유를 관리한다.
- 지도를 벗어난 결과나 늦게 도착한 예전 필터 응답으로 현재 선택 카드를 덮어쓰지 않는다.
