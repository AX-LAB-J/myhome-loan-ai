# 02. 구현 PC에서 먼저 확인할 정보

이 문서는 DB와 코드를 볼 수 있는 로컬 Codex의 조사 작업표다. 사용자가 지금 이 대화에 개인정보나 DB 덤프를 전달할 필요는 없다. 확인 결과는 현지 저장소의 `docs/implementation/`에 기록한다.

## 1. 조사 순서

1. 저장소 경로, `AGENTS.md`, README, 현재 브랜치/변경 사항 확인. 사용자의 미커밋 작업을 보존한다.
2. 프론트엔드 패키지/잠금 파일과 Python 의존성, 서버 진입점, 환경변수 예시, 실행 스크립트 확인.
3. 기존 UI를 실행해 현재 화면·색·컴포넌트·라우팅·상태 저장 위치를 파악한다.
4. FastAPI 라우터/입출력 모델/서비스/ORM/마이그레이션/계산 함수/테스트를 추적한다.
5. DB 연결의 환경 구분과 읽기 전용 접근 가능 여부 확인 후, 스키마·키·관계·단위 조사.
6. 사용자별 데이터 매핑과 계산의 입력·출력을 연결한다.
7. OpenAI와 지도 연동의 설정 존재·호출 경로·동작 상태 확인. 비밀값 자체는 출력하지 않는다.
8. 미정 사항을 근거로 해결하고 필요한 질문만 모은 뒤 구현한다.

실행이 안 되면 오류·누락 설정·필요한 조치만 기록한다. 전체 환경변수 출력, 운영 DB 재생성, 전체 고객 데이터 덤프로 문제를 풀지 않는다.

## 2. 코드와 환경 조사 체크리스트

| 영역 | 확인할 내용 | 결과로 남길 것 |
|---|---|---|

| 화면 | 기존 홈/지도/채팅/사용자 선택/메뉴/모바일 컨테이너 | 기획 대비 존재·수정·신규 구분 |
| 백엔드 | FastAPI 앱, 라우터 prefix, 모델, 서비스 계층, 에러 규격 | 실제 엔드포인트 목록과 핸들러 경로 |
| 계산 | 구매력·대출·금리 비교·현금흐름 함수와 기본값 출처 | 함수/설정 파일, 입력·출력·단위·테스트 |

| 사용자 | 인증, 사용자/가구 키, 합성 고객 선택, 권한 | 사용자 식별 흐름과 모든 조회의 범위 조건 |

| 설정 | 환경변수 이름과 서버/브라우저 노출 구분 | 이름·필수 여부·설정됨/누락만 기록 |
| 테스트 | 기존 단위/통합/E2E 도구와 테스트 DB | 재사용 명령 및 안전한 fixture |

키가 존재해도 네이버 지도 브라우저 식별자와 서버용 비밀키는 다를 수 있다. 실제 제공 설정에 맞춰 확인하고 OpenAI 비밀키를 프론트 빌드 환경에 넣지 않는다. 사용하는 SDK/API의 세부 구현은 설치된 버전과 공식 문서를 기준으로 확인한다.

## 3. DB 조사 항목

### 3.1 사용자와 가구

- 개인 고객 키와 가구 키의 관계, 나이의 기준일/생년월일 파생 여부, 주택 보유 상태 코드.
- 가구 연소득과 개인 월소득이 섞이는지, 월소득 세전/세후·급여/기타소득·평균 기간.
- 합성/실데이터/혼합 여부를 판별할 메타데이터. 단순 이름 형태로 합성이라고 판단하지 않는다.
- 가구원 수 필드 존재 여부는 조사하되, ‘가구 인원수에 따른 거래’ 기능 의미는 별도 D09로 남긴다.

### 3.2 계좌·자산·지출·대출

- 기관, 계좌, 소유자, 자산 종류, 잔액, 평가금액, 통화, 마지막 갱신일, 중복 수집 키.
- 총 금융자산에 투자자산/예적금/마이너스통장 잔액이 어떻게 포함되는지.
- 거래 원장과 월 지출 집계의 관계. 계좌이체·카드 결제대금·대출 상환을 두 번 지출로 세지 않는지.
- 월 평균 지출의 기간, 취소/환불·일회성 지출 처리, 현재 주거비 포함 여부.
- 기존 대출 잔액/월 상환, 상환액의 원금·이자 포함 여부, 한도대출 사용잔액과 약정 한도의 차이.
- 직접 입력한 기타 동원 자금과 원천 잔액을 별도 저장할 수 있는지.
- 재수집이 사용자 수정값을 덮어쓰는지. 출처와 수정 이력을 구분하는 구조가 있는지.

### 3.3 부동산과 지도

- 지역 코드/이름/경계 좌표, 단지 ID/이름/주소/위경도.
- 단지별 면적 타입과 거래의 조인 키. 같은 단지 다른 면적 가격 혼합 방지.
- 최근 실거래의 의미(최신 1건/기간 평균/중앙값/참조값), 거래일/계약일/적재일 차이.
- 실제 매물과 실거래 이력은 구별. 원본은 최근 실거래 참조값 중심이다.
- 거래 건수, 단지 건수, 히트맵 거래 수, 예산 안 비율의 분모/중복 제거 기준.
- 지도의 기간 필터 값과 실제 컬럼의 의미. 준공연도/거래연도 혼동 방지.
- 구 경계 데이터 제공 파일/테이블과 사용 가능한 범위. 지도 SDK만으로 해결된다고 가정하지 않는다.

### 3.4 구매자 집계

- 지역별 구매자 대출 현황과 비슷한 조건 구매자 집계가 실제로 존재하는지.
- 비교 조건(소득/자산/지역/면적/가구 등)과 표본 기간·표본 수.
- 자기자금 비중/대출 비중의 정의·중앙값 계산 기준.
- 최소 공개 표본 수와 억제 방식. 원본에는 `○건 미만` 자리표시자만 있어 확정 수치가 없다.
- DB에 있어도 개별 타 고객 레코드를 UI/LLM으로 넘기지 않는다. 승인된 집계만 사용한다.

### 3.5 연결·동의·설정·채팅

- 연결 기관과 상태, 동의 버전/일시/문서, 최근 동기화 시각과 실패 원인.
- 외부 동의 철회 API 존재 여부, 원천 데이터와 앱 내 복사본의 구분.
- 기본 가정/사용자 가정/임시 채팅 조건을 분리할 수 있는지.
- 채팅 세션 사용자 범위, 적용 전후 값, 되돌리기 이력, 계산 버전, 만료 정책.
- 연결 해제 시 원천/복사본/캐시/계산/채팅에서 무엇을 제거하거나 무효화해야 하는지.

## 5. API·버튼 추적 표

`01_UI_SPEC.md`에 나온 ID를 빠짐없이 기록한다. 서로 같은 서버 작업을 쓰는 버튼도 UI 검수 행은 유지한다.

| 버튼 ID | 실제 프론트 파일/핸들러 | API·서비스 | 데이터/상태 변경 | 검수 결과 |
|---|---|---|---|---|
| 예: F04 | 현지 확인 후 작성 | 실제 저장·계산 경로 | finance/계산/채팅 버전 | 대기 |

이 문서에서 API 경로를 확정하지 않는다. 기존 API가 같은 기능을 지원하면 유지하고, 부족한 계약만 추가한다.

## 6. 조사 완료 기준

- 프로젝트가 실행되는지, 실행되지 않으면 정확한 이유가 기록되어 있다.
- 화면에 필요한 모든 값에 실제 출처 또는 데이터 공백이 연결되어 있다.
- 기존 계산 규칙과 UI 표현이 일치하는지 테스트 가능한 입력/출력 사례가 있다.
- 합성 여부, 사용자 범위, 단위, 출처/기준일, 삭제 범위가 식별되어 있다.
- 미확정 사업 규칙과 단순 구현 선택을 분리했다.
- 원천 개인정보/비밀값을 문서·대화로 복사하지 않았다.
